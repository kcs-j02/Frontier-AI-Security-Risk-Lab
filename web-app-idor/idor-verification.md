# Web Application IDOR Vulnerability Analysis

## 1. 目的

OWASP Juice Shopを対象に、生成AI（Gemma 3）によるセキュリティリスク分析と、実際の脆弱性検証・修正・効果検証を行う。

特に、他ユーザーの情報に不正アクセスできるIDOR/BOLA（認可不備）を対象とする。

## 2. 検証環境

| 項目 | 構成 |
|---|---|
| 仮想環境 | VMware Workstation |
| Webサーバー | Ubuntu Server |
| クライアント | Windows 11 |
| Webアプリ | OWASP Juice Shop v20.3.0 |
| コンテナ | Docker |
| 生成AI | Ollama / Gemma 3 4B |
| 通信解析 | Microsoft Edge DevTools |

修正前はポート3000、修正後はポート3001で起動した。

## 3. 脆弱性の発見

2つの検証用アカウントA・Bを作成した。

- アカウントA：買い物カゴID 6
- アカウントB：買い物カゴID 7

アカウントAでログインした状態で、次のAPIを呼び出した。

```http
GET /rest/basket/7
```

結果、HTTP 200 OKが返され、アカウントBの買い物カゴ情報を取得できた。

この結果から、IDOR/BOLAによる読み取りの認可不備を確認した。

## 4. 原因分析

`routes/basket.ts` のソースコードを調査した。

買い物カゴIDを指定してデータを取得していたが、ログインユーザーがその買い物カゴの所有者であることを検証していなかった。

そのため、他ユーザーの買い物カゴ情報を取得できる状態だった。

## 5. Gemma 3による分析

Gemma 3に実測結果を入力し、以下の項目を分析させた。

1. 脆弱性の種類
2. 発生原因
3. 想定される影響範囲
4. 推奨する修正方法
5. 修正後に必要な検証

生成AIの回答を、HTTP通信の記録およびソースコードと比較した。

AIはアクセス制御の改善や追加検証を提案した。一方、URLパラメータの隠蔽など、認可不備の根本的な解決にはならない対策も提案した。

## 6. 脆弱性の修正

`routes/basket.ts` に認証・認可チェックを追加した。

- 未認証ユーザーを拒否する処理
- ログインユーザーの買い物カゴIDを確認する処理
- 他ユーザーの買い物カゴへのアクセスを403で拒否する処理

修正したソースコードから別のDockerイメージをビルドし、修正版を起動した。

## 7. 修正前後の比較

| 検証内容 | 修正前 | 修正後 |
|---|---|---|
| A → 自分のカゴ | 200 | 200 |
| A → Bのカゴ | 200 | 403 |
| B → 自分のカゴ | 200 | 200 |
| 未認証 → カゴ | 未検証 | 401 |

修正後は、正規ユーザーのアクセスを維持しながら、他ユーザーの買い物カゴ情報の取得を拒否できた。

なお、未認証アクセス時の401応答は、既存の認証処理による可能性がある。

## 8. 考察

今回の実験から、以下のことが分かった。

1. IDだけでデータを取得する処理では、所有者の認可確認が重要である。
2. AIによるリスク分析には有用な提案がある一方、不十分な対策も含まれる。
3. AIの判断を実際の通信やソースコードと照合する必要がある。
4. 修正後も正常なアクセスを維持できるか確認することが重要である。

## 9. 今後の課題

- 他のAPIにおけるIDOR/BOLAの検証
- データ変更・削除操作に対する認可検証
- Gemma 3とQwen 3の分析結果の比較
- AI分析の正確性を評価する基準の整備
- 修正結果と分析ログの再現可能な記録

## 10. まとめ

OWASP Juice ShopのIDOR/BOLAを実際に検証し、Gemma 3による分析、ソースコードからの原因特定、認可処理の修正、修正後の効果検証まで実施した。

本実験は、フロンティアAIを活用したセキュリティリスク分析に関心を持ち、独自に構築した学習環境で行ったものであり、NTTの実サービスを再現したものではない。
